Find every leaked secret in your GitHub orgs. Store none of them.

terces scans the full history of every repository in your organizations, blocks new secrets in pull requests and keeps one list of findings in your own Postgres. It stores an HMAC fingerprint and a short preview. It never stores, prints or sends the secret.

The pull request check fails

The service scans the commits of each pull request and posts a check run named terces. When the commits add a secret, the check fails. Make the check required in a ruleset, and the pull request cannot merge.

terces · 1 new secret in config/app.env Required · Failed

Only new secrets fail the check. A secret that already exists on the base branch is not new. The check reads .terces.yaml from the base commit, so a pull request cannot ignore its own secret.

The engine reads near the keyword

One Aho-Corasick pass finds the keywords of all 222 rules in one read of the blob. A rule runs its regex only in a window around each keyword hit, sized from the longest match the regex can make. A rule that cannot prove its matches hold a keyword runs on the full blob.

The store keeps a fingerprint, not the secret

terces computes HMAC-SHA256(key, secret) and a preview, then clears the plaintext from memory. One secret is one row, also when it occurs in many repositories. Each place is a location row.

Logs, reports, Slack alerts and pull request annotations hold the preview only. The HMAC key stays on the server, so a fingerprint alone does not reveal the secret.

The history scan finds the rest

A deleted file is still in the history. terces scan history reads every blob that any branch, tag or pull request ref reaches, one time per blob, and names the commit that added it. In this example repository, it finds 4 more secrets, among them AWS keys that a later commit removed.

You revoke it and close it

Revoke the token at its provider first. Then resolve the finding. The pull request check and the Slack alerts stop for that secret, and the audit log records who resolved it and with which database role.

What terces never does

The scanner holds a mirror of every repository and knows where every secret is. These rules keep it from becoming a new leak.

  • It never stores, prints or logs a secret. The store, the reports, the logs and the alerts hold a fingerprint and a preview such as ghp_… (40).
  • It never tests whether a key is live. A test sends the secret to a third party. Treat each finding as live until a person checks it.
  • It never puts a token in a URL or an argument. git gets the installation token as an HTTP header in its environment, never in .git/config or in ps.
  • It never trusts repository content. A file name with a terminal escape, a path with invalid UTF-8 or a 5 MB minified line cannot break the output, the store or the scan time.
  • It never passes a check without a scan. When the scan fails, the required check fails too.
  • It never opens a GitHub issue for a finding. Everyone with access to a repository can read its issues.

Quick start

You need git. Local scans need no GitHub App and no database. The exit code is 0 for no findings, 1 for findings and 2 for an error.

  1. Install the binary for macOS or Linux

    $ curl -sSfL https://bjarneo.github.io/terces/install.sh | sh

  2. Scan a directory

    $ terces scan path ~/src/my-service

  3. Scan the full history and get a report

    $ git clone --mirror https://github.com/my-org/my-repo.git && terces scan history --git-dir my-repo.git --format html > report.html

The script checks the archive against SHA256SUMS and installs to /usr/local/bin, with sudo only when that directory is not writable. To build from source instead, run git clone https://github.com/bjarneo/terces && cd terces && make build. It needs Go 1.25 or later. All releases.
